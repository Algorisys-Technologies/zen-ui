# zen-ui 10.1.0

*2026-08-01*

Two new components, in all four bindings: **Gantt**, for what a project is doing
and what is waiting on what, and **ProductionSchedule**, for what each machine is
doing and whether it can.

Nothing else changed. No existing component has a new prop, a changed default or
a different appearance, so upgrading from 10.0.0 is a version bump and nothing
else.

## Gantt — the plan, and what is waiting on what

A task tree on the left, the same rows as bars on a shared clock on the right,
dependency arrows in between.

```tsx
<Gantt tasks={plan} dependencies={links} />
```

A parent with no dates of its own gets a summary bar spanning its children and a
percentage weighted by their durations — an unweighted mean would let a one-day
task cancel out a ten-day one.

**It opens on a view fitted to your data, not on this month.** A plan running
March to November opens showing March to November; a four-hour maintenance job
opens on hours. Pinning a calendar window is still one prop away
(`defaultView="month"`), and there are quarter and year views for a plan that
outlasts a month.

```tsx
<Gantt tasks={plan} />                       // fit — the default
<Gantt tasks={plan} defaultView="quarter" />
```

**Give it a shift calendar and durations stop being wall-clock.** State when the
plant or the team is open, and a bar can be given a working duration instead of
an end date:

```tsx
const plant = {
  // 0 = Sunday. Two shifts with an hour off at noon; weekends shut.
  week: [[], shift, shift, shift, shift, shift, []],
  exceptions: [
    { date: new Date(2026, 6, 22), periods: [] },                       // holiday
    { date: new Date(2026, 6, 25), periods: [{ from: 480, to: 720 }] }, // overtime
  ],
};

// Six working hours from Friday 16:00 finishes on MONDAY, and the bar is split
// across the gap rather than drawn straight through the weekend.
{ id: "j2", name: "Heat treat", start: at(24, 16), workingMinutes: 360 }
```

**A baseline gives you slip, and the slip picks the colour.** Set `baselineEnd`
and a task that has run past it shows how far — `+2d` — and stays flagged until
it reaches 100%.

**One tab stop, arrows inside.** The chart is a `treegrid`: you tab to it once
and move with the arrow keys, `Home`/`End` for the ends of a row, `Ctrl+Home`/
`Ctrl+End` for the ends of the plan, `Enter` to activate. Bars are reachable but
not tabbable, so an eight-hundred-row plan does not put eight hundred stops
between you and the next control.

It renders the plan; it does not reschedule it. There is no drag-to-move here,
because what should happen when you move a task — push the chain, ask for
approval, who is allowed — is a policy question that belongs to your domain.
`onTaskClick` hands you the task and its derived row and you open your own
editor. The component below is the one that *does* propose changes, deliberately.

Rows are windowed at every size, with no threshold: 840 rows or 8, the same
component, and about 26 of them in the document at a time.

## ProductionSchedule — what each machine is doing, and whether it can

A sibling rather than a mode of `Gantt`, because a row here is a work centre
holding a sequence of operations, not a task holding one bar.

```tsx
<ProductionSchedule resources={cells} operations={jobs} calendar={plant} />
```

**A changeover is time the machine is busy making nothing**, so it is drawn as
its own hatched block at the head of a booking and counted in the load. A plant
that measures only run time reports itself less busy than it is by exactly its
changeovers — which is the number capacity planning turns on. And because setup
resolves through the calendar too, a 45-minute changeover starting at 16:30 on a
shift that ends at 17:00 does not finish at 17:15. It finishes at 06:15 the next
morning, and the run has not started.

**Two jobs at once on a two-operator cell is capacity being used, not an
overload.** A resource is over capacity when more of it is claimed at one instant
than it has:

```tsx
{ id: "cnc4", name: "CNC-4", capacity: 2 }   // two at once is fine
```

Overlapping work packs into lanes so a double-booking is two bars side by side
rather than one drawn over the other, and the strip underneath is load per
column — booked working time over available working time, clipped at 100% with
the overflow drawn above the line. A closed day has no utilisation at all, not
0%: an empty bar there would claim the plant was idle when it was shut.

**Changeover cost can depend on the order the jobs run in.** White paint to
black is an hour and a half of washing out; black to anything is half an hour.
No per-job number can say that, so the cost is keyed on the pair:

```tsx
const setupMatrix = {
  minutes: {
    white: { black: 90, grey: 45, "*": 20 },
    black: { "*": 30 },
    "*":   { "*": 15 },   // nothing ran before: warm-up
  },
};
```

Links carry lag as well — "start two hours after the previous operation
finishes, for cooling" — measured in working minutes like everything else.

### It reschedules, and it proposes rather than applies

Drag a bar, or focus one and press `Alt` with an arrow key (an hour a step, a day
with `Shift`). The component works out what *would* happen and hands it to you.
It changes nothing itself:

```tsx
<ProductionSchedule
  operations={jobs}
  onReschedule={(proposal) => {
    // EVERY shift, not just the one you dragged.
    const moved = new Map(proposal.cascade.map((s) => [s.operationId, s]));
    setJobs(jobs.map((j) => (moved.has(j.id) ? { ...j, start: moved.get(j.id)!.to.start } : j)));
  }}
  canReschedule={(op) => op.resourceId !== "inspection"}
/>
```

Three things that follow from that, and each is deliberate:

- **`proposal.cascade` contains the operation you dragged, first, and everything
  the routing forced along with it.** Persist only the one you dragged and you
  have written a schedule nobody saw.
- **Undo stays yours.** There is no pending state inside the component to fall
  out of step with your ERP — it renders the operations you give it, and not
  until you give it new ones.
- **Conflicts and routing cycles are reported, never enforced.** Overtime gets
  authorised, due dates get renegotiated, and a supervisor who knows both jobs
  can run may double-book on purpose. A component that refused would be wrong in
  every plant whose rules differ from the ones we guessed.

`canReschedule` gates the *affordance*, not the outcome: an operation you will
not allow to move is not draggable at all, because being told no after doing the
work of a drag feels like a fault.

### Float, and the chain that has none

"How much can I move this before it hurts?" is the question asked before every
drag. Turn on `showCriticalPath` and there is a column with the answer.

Two answers, in fact, and conflating them is the classic error. **Free float** is
how far a job slips before it disturbs its immediate successor; **total float**
is how far before it moves the end. Read the total where you meant the free and
you move one job into the next, and the cascade pushes six more. The column shows
the total and gives the free in its tooltip.

It is measured against the schedule **as it stands**, not by forward-scheduling
from zero — the jobs already have positions somebody chose, and a gap in front of
an operation is real slack rather than something to optimise away.

```tsx
<ProductionSchedule
  operations={jobs}
  dependencies={routing}
  showCriticalPath
  until={new Date(2026, 6, 24, 12)}   // the order's due date
/>
```

Pass a real due date as `until` and the reading changes: every operation can then
have *negative* float, which is the plant being late rather than a fault in the
arithmetic.

## Both, in every binding

React, Solid, vanilla and web-components, with the same API and the same
rendered output — 72 charts compared pixel-decision by pixel-decision against the
React reference. The web-components binding adds `<zen-gantt>` and
`<zen-production-schedule>`; both accept ISO date strings in markup and revive
them, including through nested task trees and calendar exceptions.

The working-time arithmetic and the scheduling maths live in
`@algorisys/zen-ui-core` and are exported: `ganttWorkingMs`, `ganttAddWorkingMs`,
`productionLoad`, `productionReschedule`, `productionCriticalPath` and the rest.
If you want to compute a schedule without drawing one, you can.
