# 10.8.1

One fix, for Solid only. Nothing was added, renamed or restyled, and no code
changes on upgrade.

## Virtualized TreeTable rows were never really measured (Solid)

If you used `<TreeTable enableVirtualization maxBodyHeight={…} />` in the Solid
binding, the virtualizer kept almost every row at the `rowEstimatedHeight`
estimate instead of the height the row actually rendered at.

With uniform rows the only symptom is a scrollbar that lies a little — the track
is sized from the estimate, so it drifts further from the truth the longer the
list. With rows of **varying** height it is worse: positions are computed from
sizes that were never corrected, so rows can sit slightly wrong and the drift
accumulates as you scroll.

Measured on a 1240-row tree whose rows render at 45px against a 44px estimate,
scrolling to the end and back:

| | total size before | after scrolling |
|---|---|---|
| React (correct) | 54617 | **54718**, retained |
| Solid (before this fix) | 54617 | 54629, falling back to 54621 |
| Solid (after) | 54616 | **54716**, retained |

Solid now tracks React to within 2px.

Nothing to change in your code — if you were working around it by setting
`rowEstimatedHeight` to your exact row height, you no longer need to, though
leaving it set does no harm.

React, vanilla and web-components were never affected.

### Why it happened, briefly

Solid applies JSX attributes *after* running an element's `ref`, and it runs the
`ref` *before* inserting the node. The virtualizer reads `data-index` off the
node to know which row it just measured, and measures the node's box — so at
`ref` time the attribute was missing and the box was empty. The measurement was
attributed to no row and thrown away, silently, with a console warning rather
than an error.

Both halves had to be fixed together: supplying the index without also deferring
the measurement makes it *worse*, because the zero-height readings then land on
real rows instead of being discarded.
