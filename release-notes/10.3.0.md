# 10.3.0

Two components for editor-shaped apps: panes you can drag apart, and a list you
can reorder. Both land in the **Solid binding first**; every package bumps to
keep one version number, but `Splitter` and `SortableList` are not in React,
vanilla or web-components yet. If you are on one of those, this release changes
nothing for you.

Nothing was removed, renamed or restyled.

## Splitter — resizable panes

```tsx
<Splitter defaultSizes={[30, 70]}>
  <SplitterPanel min={20} collapsible collapsedSize={6}>
    <Manuscript />
  </SplitterPanel>
  <SplitterHandle />
  <SplitterPanel min={30}>
    <Preview />
  </SplitterPanel>
</Splitter>
```

The handle is a child you place, not something injected between panels. An
implicit one leaves you nowhere to put a collapse button or a grab affordance,
and the handle is exactly where those belong.

**Sizes are percentages, not pixels.** A pixel-sized splitter breaks the moment
the window resizes and every consumer then writes the same resize observer.

**It writes to no storage of its own.** `react-resizable-panels` saves to
`localStorage` behind an `autoSaveId`; a component library that writes to storage
without being asked is one that surprises people. `onSizesCommit` fires once on
release — persist that wherever you actually keep state — while `onSizesChange`
fires during the drag, batched to one animation frame.

Collapsing is a snap, not a clamp: dragged past its min, a collapsible panel goes
to whichever of collapsed-or-min is nearer. And a collapsed panel reopens to at
least its min on any outward drag, so it never becomes a trap you can only escape
in code.

The keyboard contract is the real WAI-ARIA window splitter, not an approximation:

| Key | Effect |
|---|---|
| Arrow along the axis | 1% |
| Shift + arrow | 10% |
| Home / End | preceding panel to its min / max, exactly |

The divider carries `role="separator"`, `aria-controls` pointing at the panel it
resizes, and `aria-valuenow` as that panel's percentage. Under RTL the horizontal
axis mirrors — the left arrow grows the preceding panel — while vertical is left
alone, because down is down in every writing direction.

It is drawn as a hairline with a **12px hit area**, because a 1px drag target is
unusable on touch, and the resize cursor is held across the whole splitter while
a drag is live rather than only over the line.

## SortableList — reorder by drag or entirely by keyboard

```tsx
<SortableList items={ids()} onReorder={setIds}>
  <For each={ids()}>{(id) => (
    <SortableListItem id={id}>
      <SortableListHandle />
      <ChapterRow id={id} />
    </SortableListItem>
  )}</For>
</SortableList>
```

The drag machinery was already in the library — it reorders DataTable columns and
Pivot fields. This exposes it, so an app that wants reorderable chapters stops
rebuilding it. No new dependency.

**`items` is always controlled.** There is deliberately no uncontrolled mode: a
sortable list holding its own order silently disagrees with the array you
rendered from, and the bug surfaces as a row snapping back a second after the
drop.

**`handle` defaults to `true`.** Whole-item dragging is the wrong default for a
library — real rows hold buttons, links and selectable text, and making the row a
drag target breaks all three. Pass `handle={false}` for rows that are genuinely
just a label.

Full keyboard reordering, which the underlying drag library does not provide at
all:

| Key | Effect |
|---|---|
| Tab | focus a handle |
| Space / Enter | pick up, and again to drop |
| Arrow along the axis | move one position |
| Home / End | move to first / last |
| Escape | cancel, restoring the original order exactly |

An arrow or an Escape with nothing picked up is **not** claimed — so a sortable
list inside a dialog does not stop the dialog closing.

Every pick-up, move, drop and cancel is announced to a polite live region, with
English defaults so the common case needs no configuration and an
`announcements` prop for a localised app.

## Why the keyboard layer lives in core

Worth stating because it shapes the API in every binding. `@thisbeyond/solid-dnd`
ships **no keyboard handling at all** (measured: zero files in its dist mention
`keydown`), and the vanilla and web-components bindings have no drag library
whatsoever. Three of the four need a keyboard layer written by hand regardless.

So reordering-by-keyboard is `@algorisys/zen-ui-core/sortable` — `moveItem`,
`reduceReorder`, `keyToReorderAction` — and every binding calls it. Taking
dnd-kit's `KeyboardSensor` in React alone would have left that one binding with
different cancel semantics and different modifier handling from the other three,
which is exactly the kind of divergence a parity check compares names rather than
behaviour and so cannot see.

The same reasoning put the splitter geometry in `@algorisys/zen-ui-core/splitter`
rather than wrapping `react-resizable-panels`: it has no Solid equivalent.
