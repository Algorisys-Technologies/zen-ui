# 11.0.0

A new document surface, and two fixes that change how existing components look.

Nothing was renamed, removed or re-defaulted, and no API changed shape — but
this is a major because two things alter what already-working apps render, with
no code change on your side. Neither reflows layout; both change appearance.

## What changes without you doing anything

### 1. Dark mode gets shadows it never had

If you ship `data-theme="dark"`, elevated surfaces will suddenly have visible
shadows. Cards, Dialogs, Popovers, Sheets and DropdownMenus are all affected.

They were supposed to have them all along. The dark theme defined no shadow
tokens, so it inherited the light theme's near-black tint — and you cannot
darken an already-dark background with a dark colour. Measured as the peak pixel
shift a shadow made against the surface behind it:

| | `raised` | `lifted` |
|---|---|---|
| light theme | 23 / 255 | 27 / 255 |
| dark, before | **2 / 255** | **2 / 255** |
| dark, after | 22 / 255 | 27 / 255 |

Elevation in dark mode was not subtle; it was absent, and every step of the
scale looked identical.

**If you preferred the flat look**, you can have it back by overriding the
tokens — they are the public theming surface:

```css
[data-theme="dark"] {
  --zen-shadow-sm: none;
  --zen-shadow-lg: none;
}
```

Offsets, blurs and spreads are unchanged; only the shadow colour differs between
themes, so a component's elevation keeps the same shape everywhere.

### 2. Your shadow overrides now actually apply

If you have ever written something like this and wondered why it did nothing:

```tsx
<Card className="zen-shadow-[0_20px_50px_rgba(0,0,0,0.3)]" />
```

It now works. Previously `cn()` emitted **both** your class and the component's
own shadow, and the winner fell to stylesheet order — where the component's
always came later. So the override was silently dropped.

The cause was narrow enough to survive a long time: overriding one *named*
shadow with another already worked. Only named-against-arbitrary failed, because
`zen-sm` is not a value tailwind-merge recognises, so it read `shadow-zen-sm` as
a shadow *colour* and `shadow-[…]` as a shadow *size* — two groups that never
conflict.

**If a component looks different than you expect after upgrading**, check
whether you had a shadow override that was previously being ignored.

## Paper — a document surface

A sheet you read, rather than a box you put things in. `Card` remains the
generic surface; reach for `Paper` when the content is prose and the reading is
the point.

```tsx
<Paper>
  <PaperHeader>
    <PaperTitle>Kickoff notes</PaperTitle>
    <PaperDescription>Rajesh · 14 August</PaperDescription>
  </PaperHeader>
  <PaperContent>
    <p>Long-form content, capped at a readable line length.</p>
  </PaperContent>
  <PaperFooter><Button>Reply</Button></PaperFooter>
</Paper>
```

The compound shape mirrors Card's deliberately, so there is nothing new to
learn. What Card cannot express is the point:

- **`measure`** caps the sheet at a reading length — `prose` (65ch), `wide`
  (80ch), or `full`. In `ch` rather than px because the target is a line length,
  not a box: 65ch stays about 65 characters whatever the type scale does. A page
  of prose is unreadable at 1400px however nice the box is.
- **Document typography** — body leading opens up, headings tighten, and both are
  set by the component rather than inherited, so Paper reads the same under
  every theme.

The sheet centres itself, because a page lies on a desk rather than filling it.
Put it on a `bg-zen-muted` ground to get the contact its shadow implies — with
the sheet and the ground both painted `background`, the elevation has nothing to
sit on.

### `stack` — a pile rather than a sheet

```tsx
<Paper stack={1}>…</Paper>
<Paper stack={2} elevation="lifted">…</Paper>
```

One or two sheet edges behind the top one: the affordance for *this is a thread,
and there are more*, which a column of separate Papers cannot say. Purely
decorative — the edges are box-shadows, so nothing enters the DOM or the
accessibility tree, and a reader is never told the pile holds three documents
when you rendered one. It composes with `elevation`.

## A Dialog that is a document

```tsx
<DialogContent variant="paper">…</DialogContent>
```

Pass nothing and Dialog is exactly what it was. `paper` is not a restyle: a
document is **top-anchored**. Centring a long sheet vertically and then scrolling
it inside 85vh puts the first line somewhere different on every screen, and the
reader's eye has nowhere to rest. Paper mode drops the vertical centring, scrolls
the viewport rather than the panel — so the sheet's bottom edge and its margin
are visible when you reach the end, instead of the document being clipped — and
widens the cap so the measure has room to work.

## A `paper` theme

A fourth `data-theme`, alongside `default`, `zen-theme` and `dark`: warm
ink-on-paper surfaces, cut corners, a contact shadow rather than a glow, and
looser body leading.

```html
<div data-theme="paper">…</div>
```

It pairs with `Paper` but neither needs the other. The theme reaches colour,
radius, shadow and type; it cannot reach width or spacing, because the utility
layer has no tokens for those — which is exactly the gap the `Paper` component
fills. Contrast is AA throughout: body 12.7:1, muted text 5.65:1, primary 7.7:1.

## Known, and deliberately not changed

`raised` and `lifted` sit close together on the shared alpha scale — 0.10 against
0.12, which is 4/255 apart in the default theme. At small sizes the two steps are
hard to tell apart, and that is unchanged here. Pulling the scale apart would
restyle every elevated component in every theme, so it stays a separate decision
rather than being folded into this release.
