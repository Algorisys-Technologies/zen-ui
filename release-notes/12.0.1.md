# 12.0.1

One fix, Solid only: opening a dropdown menu whose `<DropdownMenuLabel>` is not
inside a `<DropdownMenuGroup>` no longer throws.

Nothing else changed, and nothing that worked before renders differently.

## Opening a Solid dropdown menu with a label in it threw

This is the shape both bindings' own documentation shows, and in Solid it threw
the first time the menu was opened:

```tsx
<DropdownMenu>
  <DropdownMenuTrigger as={Button}>Options</DropdownMenuTrigger>
  <DropdownMenuContent>
    <DropdownMenuLabel>My account</DropdownMenuLabel>
    <DropdownMenuSeparator />
    <DropdownMenuItem onSelect={editProfile}>Profile</DropdownMenuItem>
  </DropdownMenuContent>
</DropdownMenu>
```

> `[kobalte]: useMenuGroupContext must be used within a Menu.Group component`

Not a warning in the console — the render threw, so whatever error boundary was
above it caught the whole tree. In the demo that meant clicking the trigger
replaced the section with the error.

**The page itself loads clean**, which is why this could ship: the menu's content
does not mount until it opens, so nothing is wrong until someone clicks. A
smoke test that loads every route and reports no console errors passes on the
broken build — ours did.

The cause is a difference between the two libraries the bindings wrap. Kobalte's
group label reads a context that only a menu group provides, and throws when
there is none; Radix's label, which the React binding wraps, needs no group at
all. `DropdownMenuLabel` mapped straight onto the Kobalte one, so React tolerated
a standalone label and Solid did not.

Now it works in both. A label inside a group still labels that group — screen
readers announce the group by it, unchanged from before. A label with no group is
a heading, and is read as one.

Grouping was never required and still is not, but it is worth knowing what it
buys, because the two cases are genuinely different to a screen reader:

```tsx
<DropdownMenuGroup>
  <DropdownMenuLabel>Density</DropdownMenuLabel>   {/* names the group */}
  <DropdownMenuItem>Comfortable</DropdownMenuItem>
  <DropdownMenuItem>Compact</DropdownMenuItem>
</DropdownMenuGroup>
```

`DropdownMenuRadioGroup` counts as a group for this, so a label inside one names
it the same way.

## If you worked around it

Some code will have a group wrapped around a single label to get past the crash:

```tsx
<DropdownMenuGroup>
  <DropdownMenuLabel>My account</DropdownMenuLabel>
</DropdownMenuGroup>
```

That still works and there is no need to change it, but it now announces an empty
named group. If the label is just a heading over the items that follow, unwrap it.
